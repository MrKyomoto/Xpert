# PBL 教案磨课多智能体系统 — 设计方案

第二组

## 一、课题背景

本系统以 **多 Agent 圆桌研讨** 为核心思路，构建了 3 位差异化专家 + 主持人 + Judge 的多轮迭代打磨闭环。

## 三、核心设计

### 3.1 多角色圆桌并行

#### 角色定义

| 角色 | role_id | 职责 | 技能加载策略 |
|------|---------|------|-------------|
| 素养导向教研员 | r_literacy | 评价 F 维度（素养导向性），关注课标转化、思维显性化、情境真实性 | 核心 3 技能预注入 + 其余按需 |
| 学科内容专家 | r_subject | 评价 C/E 维度（内容准确性和语言逻辑性），发现知识硬伤和表述问题 | 核心 3 技能预注入 + 其余按需 |
| 学情适配专家 | r_learner | 评价 A/B/D 维度（结构/内容/一致性），关注开放度、支架、差异化 | 核心 3 技能预注入 + 其余按需 |
| 主持人 | r_chair | 汇总合并、冲突仲裁、G1 保真检测 | 全量注入 |
| 评审专家 | r_judge | 按附录A六维度评分，决定 should_stop | 单文件 _system.md |

#### 并行机制

- 每轮开始，3 位专家通过 `ThreadPoolExecutor(max_workers=3)` 并行调用 LLM
- 主持人和评审专家需等全部专家完成后才执行（同步屏障）
- 总耗时 ≈ 最慢的专家耗时 + 主持人耗时 + 评审耗时

### 3.2 每轮流程

```
Round N 的输入：
  - current_lesson      ← 第 N-1 轮打磨后的教案
  - prev_feedback       ← 第 N-1 轮 Judge 的总体评语
  - prev_total_score    ← 第 N-1 轮总分（用于温度控制和修改力度引导）
  - prev_opinions_text  ← 第 N-1 轮各专家的意见（用于互评引用）

Step 1: 3 位专家并行思考
  - 输出格式：思考内容 + "---OPINION---" + 修改意见列表
  - 失败重试：最多 3 次，指数退避（1s, 2s），全失败输出占位意见
  - temperature 根据 prev_total_score 动态调整

Step 2: 主持人合并
  - 收到所有专家的修改意见 → 冲突检测与仲裁
  - 输出格式：合并思路 + "---POLISHED---" + 完整教案 Markdown

Step 3: Judge 评审
  - 按附录 A 六维度评分：A结构(10) B内容(15) C准确(20) D一致(15) E语言(10) F素养(30)
  - 输出 JSON：各维度 score/evidence/suggestions + total_score + should_stop
  - 0 分时最多重试 3 次

Step 4: 终止判断
  - 首轮强制继续
  - 总分 >= 85 且提升 < 2 分 → 停止
  - 总分 < 85 → 必须继续
  - 达到 5 轮上限 → 强制停止
```

### 3.3 动态 Temperature

| 上一轮总分 | temperature | 修改策略 |
|-----------|-------------|---------|
| >= 90 | 0.3 | 保守微调，不提大改动 |
| 80–89 | 0.5 | 适度改进 |
| 70–79 | 0.7 | 正常输出 |
| < 70 | 0.9 | 大胆提结构改进 |

此策略在专家和主持人中均生效，确保高分时输出稳定、低分时有足够探索空间。

### 3.4 Skill 技能系统

#### 设计理念

Agent 的 system prompt 不硬编码在 Python 代码中，而是以 `.md` 文件形式存储在 `skills/{role_id}/` 目录下。支持三种加载策略：

1. **预注入**：核心技能直接写入 system prompt（如 responsibility.md, rubric_mapping.md）
2. **索引**：其余技能只显示名称和描述，不加载内容
3. **按需加载**：LLM 通过 `load_skill` 工具调用，将技能全文注入上下文

#### 文件示例

```
skills/r_literacy/
├── _system.md            ← 角色身份 + 核心职责 + 输出格式
├── responsibility.md     ← 预注入：核心职责详情
├── rubric_mapping.md     ← 预注入：量规条款对应关系
├── knowledge_boundary.md ← 预注入：学术边界和转交规则
└── case_knowledge.md     ← 按需加载：金标准案例知识
```

#### 优势

- 新增角色只需新建目录 + 写 `_system.md`，无需改 Python 代码
- 技能文件可独立修改维护，不影响系统运行
- 按需加载避免一次性注入过多文字导致 token 浪费

### 3.5 容错机制

| 故障场景 | 处理策略 |
|---------|---------|
| 专家 API 调用失败 | 最多重试 3 次（指数退避 1s/2s/4s），全失败输出占位意见，不崩流程 |
| Judge 返回 0 分 | 最多重试 3 次，日志打出原始响应供调试 |
| 首次轮次 Judge 误判 should_stop | 代码层强制 `prev_total_score is None → should_stop = False` |

### 3.6 日志系统

`run.py` 通过 `capture_output()` 将 `sys.stdout` 替换为 `Tee` 对象，同时写入终端和 `logs/{时间戳}.log`。日志包含：

- 每轮每位专家的完整思考内容和修改意见
- 主持人的冲突分析和合并思路
- Judge 评分明细及原始响应（0 分时输出 DEBUG 信息）
- 每轮专家耗时、temperature 参数
- 总运行耗时

## 四、附录 D 合规

### 4.1 文件命名

输入：`{学号}_{样本ID}.md`（如 `demo001_MATH01.md`）
输出：`{学号}_{样本ID}_polished.md` + `{学号}_{样本ID}_process.json`

可执行 `validate_submission.py` 进行格式自查。

### 4.2 process.json 结构

```json
{
  "meta":    { "student_id", "sample_id", "timestamp" },
  "roles":   [ { "role_id", "name", "expertise" } ],
  "discussion": [ { "round", "role_id", "content", "refers_to" } ],
  "modifications": [ { "mod_id", "location", "before_summary", "after_summary", "source_role", "rationale" } ]
}
```

### 4.3 运行契约

```bash
python code/run.py --lesson <path> --profile <path> --out <dir>
```

- 退出码：0 = 成功，非零 = 失败
- 支持 `--judge` 参数实现仅评审模式
- 支持长文本教案（MAX_TOKENS=16000）

### 6.1 单 Agent vs 多 Agent 对比实验

以 MATH03（降质版）为对照样本，同一输入分别用单 Agent 改写和多 Agent 圆桌打磨：

| 对比维度 | 单 Agent（baseline） | 多 Agent（正式版） |
|---------|-------------------|------------------|
| 学情分析 | ❌ 无 | ✅ 包含（学生基础、前概念误区） |
| 教材分析 | ❌ 无 | ✅ 跨学科定位 |
| 元评论污染 | ✅ 带"作为专家"自述（评审被剥离） | ❌ 干净输出 |
| 可执行颗粒度 | 活动描述较粗 | ✅ 精确到分钟、区分师生活动 |
| 学生前概念应对 | ❌ 无 | ✅ 明确列出典型误区 |
| 篇幅 | ~33KB | ~63KB |

结论：多 Agent 在结构完整性、内容颗粒度、学情针对性上均优于单 Agent。

## 七、方法论转化：案例/量规 → 角色与评审设定

### 7.1 从附录B金标准案例到专家角色

研读附录B的5个脱敏金标准案例（化学、数学、生物、语文、环境），归纳高质量教案共性特征：

| 提炼的设计手法 | 映射到的专家角色 | 具体体现 |
|--------------|----------------|---------|
| 驱动性问题设计、素养目标行为化 | r_literacy（素养导向教研员） | F维度评审，check目标是否绑定课标素养语言 |
| 知识准确性、例题/实验方案正确性 | r_subject（学科内容专家） | C/E维度评审，发现知识硬伤和逻辑问题 |
| 学情适配、开放度调控、支架搭建 | r_learner（学情适配专家） | A/B/D维度评审，评估认知负荷和差异化设计 |
| 冲突仲裁、保真检测 | r_chair（主持人） | 汇总专家意见，检测G1保真 |

### 7.2 从附录A量规到Judge评审

附录A《教案质量评价量规》是Judge prompt的核心来源：

- **维度权重**（A=10, B=15, C=20, D=15, E=10, F=30）直接复制到Judge的评分JSON Schema
- **子指标计点规则**（每项0/1/2）转化为评分要求
- **排他条款**（同一处原文只计入一个维度）编码为评审约束
- **特异性检验**（"换一节课是否成立"）作为F维度判2的关键条件

### 7.3 转化中的取舍

| 量规要求 | 实现程度 | 取舍说明 |
|---------|---------|---------|
| C维度3次独立采样+去重 | 部分实现 | 当前仅1次LLM调用，未做多模型聚合 |
| 人工复核（C重大错误/F深评） | 未实现 | 验收环境不支持人工干预 |
| 反评审对抗（剥离自述内容） | 已实现 | Judge prompt明确要求不采信"设计意图"自评 |
| 评审器冻结+版本号 | 已实现 | skill文件独立维护，修改需重新校准 |

## 八、局限性

1. **单模型评审**：Judge仅依赖单一LLM调用，未实现附录A要求的3次独立采样+去重机制，评审稳定性和C维度重大错误的召回率有限
2. **无人工复核**：缺少"人工确认C错误+F维度深评"环节，当前流水线相当于Tier1自评
3. **profile未深度使用**：学情描述文件仅读取student_id用于校验，未真正影响专家意见的开放度调适
4. **技能覆盖不全**：部分附录A判据（如PBL课型双轨量规强检）未在Judge prompt中显式编码，依赖LLM本身的知识
5. **无保真测试集验证**：G2改劣检测未用正式植入缺陷集验证，当前仅靠人工审查
