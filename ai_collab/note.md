# AI 协作开发记录

> 本记录总结了使用 Claude Code 辅助开发"多智能体圆桌磨课系统"过程中的实践心得与关键提示词设计。

## 一、开发模式

本项目采用 **Claude Code CLI** 作为主开发工具，在 Windows (Git Bash) 环境下完成全部编码。整个开发过程通过多轮对话迭代完成，从单 Agent 原型逐步演进为多 Expert+Chair+Judge 的完整圆桌架构。

### 工作流

1. **需求分析**: 用户提供 PBL 课题需求文档（Word），Claude 提取关键需求并逐项确认
2. **架构设计**: 以对话形式讨论技术方案，Claude 输出目录结构，用户确认后落地
3. **增量编码**: 每轮对话聚焦一个子问题（如 skill 管理器、并行调度、Judge评审），快速产出可运行代码
4. **测试验证**: 用户在实际环境运行，反馈问题，Claude 修复——形成"需求→编码→运行→反馈→迭代"闭环

## 二、关键提示词设计

项目的核心工程制品集中存储在 `code/skills/{role_id}/` 目录下，每个角色有独立的 prompt 文件包。下面提炼设计思路，具体内容见对应 `.md` 文件。

### 2.1 专家角色系统 prompt 设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **角色锚定** | 每个角色固定视角，不越界 | r_literacy 只评素养维度，不评知识准确性 |
| **量规绑定** | 评价依据来自附录A量规，不是模型常识 | rubric_mapping.md 将维度映射为可操作指令 |
| **边界声明** | 明确告知模型"你不知道什么" | knowledge_boundary.md 列出该角色不应处理的问题 |
| **按需加载** | 不把全部知识塞进上下文 | load_skill 工具让专家在需要时自己拉取补充知识 |

### 2.2 评审专家（r_judge）单文件设计

Judge 是系统里最重要的 prompt，因为它决定了评分一致性和终止条件。最终采用**单文件设计**（`code/skills/r_judge/_system.md`），不拆分技能，原因：

- 多文件拆分导致 Judge 评分不一致，同一教案不同次评审分数波动大
- Judge 不使用工具（use_tools=False），无法调用 load_skill
- 全量注入确保每次评审都基于完整量规上下文

### 2.3 主持人冲突仲裁设计

chair 的 prompt 重点在于：
- 检测专家意见间的冲突（同一处修改不同专家给出相反建议）
- 冲突原因归类（立场分歧 / 事实分歧 / 优先级分歧）
- 裁决策略（折中方案 / 按角色优先级 / 按学情裁定）
- 输出严格格式 `---POLISHED---` 分隔思考和教案

## 三、Agent 用法心得

### 3.1 ThreadPoolExecutor + 3x Retry

```
优势: 3位专家并行调用，总耗时≈最慢专家耗时，而非串行之合
坑: 单专家失败不应崩全局 → 3次重试 + 占位输出
坑: Python线程池内异常在主线程不自动抛出 → 用 future.result() 捕获
```

### 3.2 动态 temperature 控制

根据上一轮总分动态调整创造力：

| 总分 | temperature | 策略 |
|------|-----------|------|
| ≥90 | 0.3 | 保守微调，防止过度修改降低分数 |
| 80-89 | 0.5 | 适度调整 |
| 70-79 | 0.7 | 正常力度 |
| <70 | 0.9 | 大胆重构 |

回滚恢复时再降一档，确保恢复后的修改稳妥。

### 3.3 最佳版本回滚

```
遇到的最大问题: 越磨越差——第3轮评分低于第2轮
解决: 跟踪 best_lesson / best_score，分数下降时自动回滚到最佳版本
上限: 连续回滚2次仍下降则强制终止
```

### 3.4 附录 D 格式自动校验

输出后自动调用 `validate_submission.py` 自检，确保格式合规。这个设计显著减少了手动检查的时间投入，也避免了提交时的格式返工。

## 四、经验总结

| 主题 | 结论 |
|------|------|
| **单模型基线先行** | 先搭单 Agent 改写作为baseline，再引入多Agent，对比效果 |
| **多文件 prompt 管理** | skill 分开好维护，但 Judge 必须单文件保一致性 |
| **格式解析比想象重要** | `---OPINION---` `---POLISHED---` 分隔符的解析鲁棒性决定了系统的稳定性 |
| **回滚机制不可少** | 多轮迭代必然出现分数震荡，无回滚机制的系统不完整 |
| **非流式优先** | 线程池并行时流式输出意义不大，反而增加工具调用复杂度 |
